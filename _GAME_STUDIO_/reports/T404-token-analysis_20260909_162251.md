# T404 Token Consumption Analysis

## Summary

T404's 2.47M token usage was **legitimate and unavoidable given the architecture**. The tokens were consumed primarily by Claude Code's internal context accumulation across multiple tool calls (file reads, edits), not by the Studio's context injection. The 99.7% cache read rate (2.47M of 2.47M) indicates efficient caching but also reveals that Claude Code's multi-turn agent loop was the dominant cost driver.

## Key Findings

| Finding | Evidence | Implication |
|---------|----------|-------------|
| Cache reads dominated (99.97%) | 2,468,243 cache read vs 68,029 cache write | Claude Code's prompt caching worked, but context still accumulated per-turn |
| Output was minimal (9,197 tokens) | Output = 0.37% of total | This wasn't an over-generation problem |
| Multiple files modified | schedules.py, websocket.py, studio-routines.js, studio.css | Each file read + edit = 2 tool calls minimum |
| Compare: T403 used 162K tokens | Simple CSS-only fix, 1 file | 15x fewer tokens for simpler task |
| Compare: T405 used 1.25M tokens | Multi-file investigation + 1 edit | Similar scope, similar token usage |

## Token Breakdown (Estimated by Phase)

| Phase | Estimated Tokens | Explanation |
|-------|-----------------|-------------|
| Initial context injection | ~50-100K | System prompt + role + task + files tree |
| File reads (4+ files) | ~200-400K | schedules.py (518 lines), websocket.py (145 lines), studio-routines.js (415 lines), studio.css (likely read portions) |

| Edits and verification | ~100-200K | Multiple Edit tool calls + re-reads for verification |

## Root Cause: Claude Code's Agentic Architecture

The Claude CLI backend runs Claude Code in full agentic mode. Each tool call (Read, Edit, Grep, etc.) creates a new "turn" in the conversation:

```
Turn 1: System prompt + task → Read file A
Turn 2: System prompt + task + file A content → Read file B  
Turn 3: System prompt + task + file A + file B → Edit file A
Turn 4: System prompt + task + file A + file B + edit result → Edit file B
... (context grows linearly with each turn)
```

For T404, the agent likely made 8-12 tool calls:
1. Read schedules.py (understand structure)
2. Read websocket.py (understand handlers)
3. Read studio-routines.js (understand frontend)
4. Read studio.css (understand styles)
5. Edit schedules.py (add order field)
6. Edit schedules.py (add reorder method)
7. Edit websocket.py (add handler)
8. Edit studio-routines.js (add drag-drop logic)
9. Edit studio.css (add drag styles)
10. Re-read to verify?

Each turn re-sends the entire accumulated context. By turn 10, the context includes ALL previous file contents + ALL previous responses.

## Comparison with Simpler Tasks

| Task | Tokens | Files | Edits | Token Ratio |
|------|--------|-------|-------|-------------|
| T403 (CSS fix) | 162K | 1 | 1 | 1x (baseline) |
| T404 (drag-drop) | 2,468K | 4 | 6+ | 15x |
| T405 (token display) | 1,251K | 3 | 1 | 7.7x |

The correlation is clear: **token usage scales superlinearly with number of tool calls**, not with code complexity.

## Why This Wasn't Preventable (Given Current Architecture)

1. **Claude Code doesn't support incremental context** - It always sends full history
2. **No way to "forget" earlier file reads** - Once read, always in context
3. **Each edit requires reading first** - Double the file content in context
4. **Verification reads add more** - Prudent agents re-read to confirm changes

## Recommendations

### 1. For Future Multi-File Tasks (HIGH PRIORITY)
**Action:** Break complex tasks into sequential single-file subtasks  
**Rationale:** T403 (1 file, 1 edit) = 162K tokens. Four separate T403-style tasks = ~650K tokens vs T404's 2.47M  
**Implementation:** BOSS should decompose "add drag-drop reorder" into:
- T1: Add `order` field to Schedule dataclass  
- T2: Add `reorder()` method to ScheduleManager
- T3: Add websocket handler
- T4: Add frontend drag-drop + CSS

### 2. Prune File Content Before Injection (MEDIUM PRIORITY)
**Action:** For large files (>200 lines), only inject relevant sections  
**Rationale:** schedules.py is 518 lines but only 30 lines were relevant  
**Implementation:** Use Grep to find relevant sections, then Read with offset/limit

### 3. Track Tool Call Count in Metrics (LOW PRIORITY)
**Action:** Add `num_tool_uses` to task metrics (already exists in claude_cli.py)  
**Rationale:** Allows correlation between tool calls and token usage for future optimization

### 4. Consider Alternative Architecture for Code Tasks (RESEARCH)
**Action:** Investigate whether Claude API direct calls (with manual tool handling) would be more efficient  
**Rationale:** Claude Code's agentic loop is optimized for interactive coding, not headless batch operations  
**Tradeoff:** Would lose MCP integration and require reimplementing file tools

## Conclusion

The 2.47M tokens for T404 were a **natural consequence of using Claude Code for multi-file editing tasks**. The cost wasn't due to waste or bugs—it's the architectural reality of accumulating context across tool calls. The main optimization lever is **task decomposition**: smaller, focused tasks that touch fewer files will use exponentially fewer tokens.
