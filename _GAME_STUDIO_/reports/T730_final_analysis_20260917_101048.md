## Root Cause: RACE CONDITION

### Scenario
Two TaskManager instances (or disk sync during save):

**Thread A (studio.py):**
```
1. complete_task() acquires lock
2. Sets status = APPROVED in memory
3. Calls _save_tasks()
4. Releases lock
```

**Thread B (MCP or sync):**
```
1. _sync_tasks_from_disk() acquires lock AFTER step 2 but DURING step 3
2. Reads disk (still has status=in_progress)
3. Overwrites memory status back to in_progress
4. Returns (memory now stale)
```

**Result:** When atomic_json_write completes, it serializes the STALE memory state.

### Supporting Evidence

```python
# tasks.py:620-628 - _sync_tasks_from_disk()
disk_status = task_data.get("status")
mem_status = self.tasks[task_id].status.value
if disk_status and disk_status != mem_status:
    # Status changed on disk - update in memory
    self.tasks[task_id].status = TaskStatus(disk_status)  # ❌ OVERWRITES APPROVED
    logger.info("Synced status change: %s %s -> %s", task_id, mem_status, disk_status)
```

**This sync happens DURING complete_task() execution, reverting the status change.**

## Why Only Status Was Affected

The sync only updates `status` and `error` fields (line 625-626), not output_response or completed_at. So:
- completed_at: Set by complete_task, not touched by sync ✓
- output_response: Set by complete_task, not touched by sync ✓
- status: Set by complete_task, REVERTED by sync ❌

## Fix Required

The lock protects individual operations but NOT the save+sync sequence. Need to either:
1. Hold lock during entire _save_tasks() + disk flush
2. Disable sync during complete_task()
3. Make _save_tasks() check if status changed during write
