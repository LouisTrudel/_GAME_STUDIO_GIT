## Bug Confirmed

**Task T729 has inconsistent state in data/tasks.json:**
- ✓ `completed_at`: "2026-09-17T10:03:21.654876" (SET)
- ✓ `output.response`: Contains full agent response with "T729 COMPLETED" (SET)
- ✗ `status`: "in_progress" (SHOULD BE "approved")

### Evidence of Partial Persistence
The fact that `completed_at` and `output_response` were persisted but `status` was NOT suggests:

1. **Not a race condition** - If another thread overwrote the file, ALL fields would be wrong
2. **Not a lock failure** - The lock is held for the entire complete_task() scope
3. **Not a serialization bug** - to_dict() line 297 correctly does `self.status.value`

### Most Likely Cause: MCP Write-After-Complete

**Hypothesis:** The MCP server (mcp_server.py) may be writing tasks.json AFTER studio.py completes the task, overwriting the status back to in_progress.

**Evidence:**
1. T729's output and completed_at are correct (set by complete_task)
2. T729's status is wrong (reverted to in_progress)
3. MCP server has direct file access to data/tasks.json

**Flow:**
```
1. FleetCLI agent completes T729
2. studio.py:661 calls complete_task()
3. tasks.py:813 sets status=APPROVED
4. tasks.py:818 calls _save_tasks() → writes to disk with status=approved
5. MCP server updates task (via direct file write or stale in-memory state)
6. MCP overwrites status back to in_progress (BUT keeps completed_at/output)
```

### Why Only Status Was Reverted

The MCP server likely:
- Reads the task from its stale in-memory cache
- Updates specific fields (completed_at, output)
- Writes back to disk
- BUT uses stale status=in_progress from its cache
