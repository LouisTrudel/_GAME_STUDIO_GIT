- `input.role_md`, `input.skills`, `input.task_prompt` (full content)
- `result` duplicate (kept in `output_response` and deliverables/)

### Analysis of 4 Requested Optimizations

#### 1. Can input context use path references instead of full content?

**Status: Already Implemented (T199)**

The `to_dict()` method no longer serializes:
- `input_role_md` → Was `role.md` content (~2-5KB per task)
- `input_skills` → Was combined skills content (~5-20KB per task)
- `input_task_prompt` → Was full prompt (~1-50KB per task)

These fields still exist in the dataclass for runtime use but are **not persisted to JSON**.

**No action needed** - path references would require additional storage and lookup logic with no benefit since content isn't stored anyway.

#### 2. Consolidate output vs result duplication

**Status: Partially Resolved**

| Field | Purpose | Storage |
|-------|---------|---------|
| `output_response` | Runtime: new schema | Not in to_dict() |
| `result` | Legacy compat | Not in to_dict() |
| `data/deliverables/T###.md` | Permanent storage | Filesystem |

**Current behavior:**
- `complete_task()` writes to both `output_response` and `result` (line 450-453)
- `save_deliverable()` writes to filesystem (line 460)
- Neither is serialized to `tasks.json`

**Recommendation: REMOVE `result` field entirely**

| Action | File | Change |
|--------|------|--------|
| Delete field | `tasks.py:178` | Remove `result: Optional[str] = None` |
| Update setter | `tasks.py:451-453` | Remove `task.result = result` |
| Update fail_task | `tasks.py:469` | Use `task.error` instead of `task.result` |
| Update from_dict | `tasks.py:292` | Remove fallback |
| Update retry_task | `tasks.py:680` | Remove `task.result = None` |

**Risk:** Low - `result` is only used in `to_context_string()` for preview, which can use `output_response` instead.

#### 3. Compress execution metrics to token I/O only

**Status: Already Implemented**

Current `execution` block contains only:
```python
"execution": {
    "errors": self.exec_errors or self.tool_errors,
}
```

All other execution metrics (`duration_ms`, `num_turns`, `num_tool_uses`, `api_retries`) are **not serialized**.

**Question:** Should `execution.errors` also be dropped?

| Option | Pros | Cons |
|--------|------|------|
| Keep errors | Debug value, pattern detection | ~50-500 bytes/task |
| Drop errors | Minimal schema | Lose debug info |

**Recommendation: KEEP errors** - They're essential for identifying recurring issues (API failures, tool crashes). Storage cost is negligible.

#### 4. Group friction points into single field

**Status: Not Yet Implemented (from T199 spec)**

The T199 spec mentioned adding `friction.category` enum but it wasn't implemented. Current schema lacks friction tracking.

**Proposed addition:**
```python
# Add to to_dict():
"friction": self._compute_friction_category()

def _compute_friction_category(self) -> Optional[str]:
    """Derive friction category from execution data."""
    if self.exec_is_error or self.error:
        return "error"
    if self.retry_count > 0:
        return "retry"
    if self.exec_errors:
        return "tool_error"
    if self.cost_usd > 1.0:  # Expensive task
        return "high_cost"
    return None  # Clean execution
```

| Category | Trigger | Analysis Value |
|----------|---------|----------------|
| `error` | Task failed/errored | Infrastructure issues |
| `retry` | retry_count > 0 | Flaky tasks |
| `tool_error` | exec_errors not empty | Tool reliability |
| `high_cost` | cost_usd > threshold | Optimization targets |
| `null` | Clean run | Baseline |

**Recommendation: ADD friction category** - Enables filtering archived tasks by problem type without storing verbose data.
