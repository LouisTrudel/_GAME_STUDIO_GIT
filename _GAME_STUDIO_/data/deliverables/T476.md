### Potential Issues Found

| Issue | Evidence | Impact |
|-------|----------|--------|
| MCP sync race | `reload_from_disk()` only adds new tasks | Could miss status updates from MCP |
| No status sync | Disk sync doesn't update existing task status | BOSS may see stale status if MCP changed it |
| Multiple processes | `claimed_process_id` tracks, but MCP and server are separate | Status divergence possible |

### Key Finding: Status Desync Risk

BOSS uses `task_manager.get_task()` which reads from **in-memory state**. If MCP server modifies `tasks.json` directly (e.g., marks task ERROR), the web server's in-memory copy won't update unless:
1. New task is added (triggers `reload_from_disk`)
2. Server restarts

## Recommendation

**Root cause**: BOSS confusion likely from status desync between MCP process and web server process. Both share `tasks.json` but only sync NEW tasks, not status updates.

**Fix options**:
1. Add periodic `_reload_task_statuses()` to sync all statuses from disk
2. Use file lock + full reload on every `get_task_status()` call
3. Switch to shared database instead of JSON file
