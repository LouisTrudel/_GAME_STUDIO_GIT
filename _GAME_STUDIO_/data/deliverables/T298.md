## Deliverable: T298 - Fix Discuss Timeout Error Display

### Root Cause
- **Frontend timeout**: 30 seconds
- **Backend behavior**: Runs Boss and Research agents sequentially (each with 30s individual timeout), taking up to 60+ seconds total
- **Result**: Frontend timeout fires before backend completes, showing false error even on successful discussions

### Fix Applied
**File**: `studio-suggestions.js:625-665`

1. **Increased frontend timeout** from 30s to 90s (60s backend max + 30s buffer)
2. **Improved timeout message** from hard error to soft warning: "Discussion taking longer than expected - check Hub for updates"

### Changes
```javascript
// Before
const timeoutId = setTimeout(() => controller.abort(), 30000); // 30s timeout
// ...
if (e.name === 'AbortError') {
    showNotification('Discussion request timed out', 'error');
}

// After  
const timeoutId = setTimeout(() => controller.abort(), 90000); // 90s timeout
// ...
if (e.name === 'AbortError') {
    // Timeout - but agents may still complete and post to Hub
    showNotification('Discussion taking longer than expected - check Hub for updates', 'warning');
}
```

### Why 90 seconds
Backend `routes.py:418` uses `TIMEOUT_SECONDS = 30` per agent. Since agents run in a ThreadPoolExecutor but results are collected sequentially (boss.result() then research.result()), worst case is ~60 seconds. The 90-second frontend timeout provides margin for network latency and processing overhead.
